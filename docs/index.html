PiauíBench

Benchmark de 10 questões de múltipla escolha (5 alternativas) sobre geografia, história e demografia do Estado do Piauí, usado para comparar a acurácia de três LLMs pequenos executados localmente via Ollama.

Resumo

Acertos consolidados e custo de inferência por resposta.

Controle de viés posicional

O teste: as mesmas 10 questões são reaplicadas com a ordem das cinco alternativas permutada a cada repetição. O conteúdo não muda — só a letra em que a resposta correta aparece. O gabarito é remapeado junto, então a acurácia continua comparável.

Por que isso importa: um modelo pode acertar a múltipla escolha sem saber a resposta, bastando ter preferência pela letra em que o gabarito calhou de estar. Sob ordem fixa, preferência por letra e conhecimento produzem exatamente o mesmo número — a acurácia isolada não distingue os dois.

Como ler: conhecimento sobrevive à permutação, preferência por letra não. Barras iguais = o acerto vinha de conhecimento. Queda em direção a 20% (o acaso com 5 alternativas) = parte do acerto original era artefato da posição do gabarito. A altura da barra hachurada é a estimativa menos contaminada; a diferença entre as duas quantifica o quanto a medição de ordem fixa estava inflada.

Barra sólida: ordem fixa Barra hachurada: ordem cíclica Bigode: IC 95%

Distribuição das letras escolhidas

Frequência de cada letra na execução com permutação. Como a permutação espalha o gabarito uniformemente pelas cinco posições, um modelo sem viés responderia cerca de 20% em cada letra. Concentração acima disso é a assinatura direta do viés: mede a preferência pela posição, independentemente do conteúdo da alternativa.

Acerto por questão

✓ = acertou (maioria das repetições) · ✗ = errou. A letra mostrada é a resposta mais frequente do modelo.

Rodar o benchmark no seu Ollama

A página chama a API local do Ollama direto do navegador. Nada sai da sua máquina.

Pré-requisito (CORS). Servindo esta página de localhost, o Ollama já aceita a conexão por padrão. Abrindo pelo GitHub Pages, é preciso autorizar a origem: 
OLLAMA_ORIGINS="https://gutoportelaa.github.io" ollama serve
No Linux com systemd: systemctl edit ollama, adicione Environment="OLLAMA_ORIGINS=https://gutoportelaa.github.io" e reinicie o serviço. Depois clique em Conectar.

Chrome, Edge e Firefox tratam localhost como origem confiável e permitem a chamada mesmo a partir de uma página HTTPS. No Safari, sirva a página localmente (python3 -m http.server -d docs 8000) em vez de usar o GitHub Pages.

Como as questões chegam a outros usuários

O GitHub Pages serve arquivos estáticos: não há servidor, banco nem sessão. O localStorage é privado do seu navegador — ninguém mais vê suas questões até que elas entrem no repositório. O repositório é o banco de dados compartilhado.

Fluxo
editor → Compartilhar abre uma issue já preenchida → revisão do gabarito contra a fonte → merge em docs/benchmark.json → CI reexecuta o benchmark → results.json commitado → Pages publica para todos.

Nenhuma das etapas exige backend. A revisão humana entre a proposta e o merge é deliberada: um gabarito errado contamina a métrica de todos os modelos, e o campo fonte é o que torna isso auditável.

Se preferir contribuir direto pelo git:

mv ~/Downloads/benchmark.json docs/benchmark.json
python3 bench/run_bench.py --runs 3
python3 bench/run_bench.py --runs 5 --shuffle --out docs/results_shuffle.json
git commit -am "Adiciona questões sobre X" && git push

O push em docs/benchmark.json dispara o workflow benchmark.yml, que instala o Ollama no runner, reexecuta as duas variantes e commita os resultados — não é preciso ter GPU nem rodar nada localmente.

Regra de qualidade: as cinco alternativas devem ser plausíveis e do mesmo tipo (todas municípios, todos anos, todos rios). Distrator absurdo reduz o problema a menos de cinco opções efetivas, inflando a acurácia sem que o modelo saiba mais.

Metodologia

Como a acurácia é medida.

  • Tarefa: QA de múltipla escolha (MCQA) fechada, sem contexto recuperado — mede conhecimento paramétrico regional em pt-BR.
  • Prompt: um system prompt fixo em português + a questão com as cinco alternativas rotuladas A–E, pedindo apenas a letra.
  • Decodificação: temperature = 0, top_p = 1, seed fixa e think: false (desliga o modo de raciocínio do Qwen3), garantindo reprodutibilidade.
  • Saída estruturada: usa o parâmetro format do Ollama com um schema JSON cujo enum é ["A","B","C","D","E"]. Isso elimina falhas de parsing e separa erro de conhecimento de erro de formatação.
  • Repetições: 1 chamada em ordem fixa + 5 em ordem cíclica, por questão e por modelo — 6 no total. Repetir prompt idêntico com temperature=0 não gera informação nova; ver o quadro abaixo.
  • Métrica: acurácia = acertos / total de chamadas, contadas individualmente. Baseline aleatório = 20% (1 em 5).
  • Limitação: com apenas 10 itens, o intervalo de confiança é largo (cada questão vale 10 p.p.). O resultado é indicativo, não conclusivo — veja "Como ampliar" no README.

Quantas vezes cada pergunta é feita

O benchmark roda em duas passadas independentes, e cada uma grava seu próprio arquivo de resultados. Por questão e por modelo:

PassadaChamadasO que muda entre elasServe para
Ordem fixa1 nada — é uma medição única a acurácia "ingênua", como um benchmark de múltipla escolha comum reportaria
Ordem cíclica5 a lista de alternativas é rotacionada em 1 posição a cada chamada o gabarito visita cada uma das cinco letras exatamente uma vez
Total6 —com 3 modelos: 18 chamadas por questão; 180 no benchmark inteiro
Por que a ordem fixa é 1 chamada, e não 3
Com temperature=0 a decodificação é gulosa: o mesmo prompt produz sempre a mesma saída. Medimos isso — nas 30 repetições da versão anterior (3 modelos × 10 questões), as 3 respostas foram idênticas em 30 de 30 casos. Repetir prompt idêntico consumia 3× o tempo sem gerar informação nova. Repetição só informa quando o prompt muda, e é por isso que todo o orçamento de repetição foi para as permutações.

Como as chamadas viram um número

Há duas agregações diferentes, e elas podem discordar — de propósito.

  • Acurácia (a métrica reportada): acertos ÷ total de chamadas, contadas individualmente. Na passada cíclica, uma questão em que o modelo acerta 1 das 5 posições contribui com 1/5 — acerto parcial existe e entra na conta.
  • ✓/✗ da tabela por questão (só exibição): voto majoritário, acertos > chamadas/2. Acertar 1 de 5 vira ✗, apesar de a questão ter contribuído com 1/5 para a acurácia. Empate conta como erro.
  • Letra exibida: a resposta mais frequente entre as chamadas, já convertida de volta para a numeração original das alternativas.
  • Variação em p.p.: subtração direta das duas acurácias — 40% → 26,7% é −13,3 pontos percentuais, não −13,3%. Em variação relativa isso seria −33%. O consolidado (bench/consolidar.py) grava as duas formas em summary.json e summary.csv.

Um modelo que responde certo em 2 das 5 posições e erra em 3 não "sabe pela metade": ele acerta quando o gabarito cai numa posição que ele favorece. É esse padrão que a passada cíclica expõe e a ordem fixa esconde.

Poder estatístico: o que 10 questões permitem concluir

Esta é a limitação mais importante do projeto, e ela é quantificável. A unidade amostral é a questão, não a chamada: repetir a mesma pergunta em 5 posições dá 50 chamadas, mas não 50 observações independentes. O erro-padrão é calculado sobre a taxa de acerto por questão (clustered standard error), como recomenda Miller (2024).

Consequência
Com 10 questões, o intervalo de confiança dos três modelos inclui o acaso (20%). Formalmente: este benchmark não demonstra que nenhum dos modelos sabe algo sobre o Piauí, nem que um é melhor que o outro. Para separar dois modelos com 10 p.p. de diferença (α=5%, poder=80%) seriam necessárias ~356 questões; para os 4 p.p. entre llama3.2:3b e qwen3:4b, ~2.260.

O que é sólido aqui é o efeito intra-modelo: a queda sob permutação é medida no mesmo conjunto de questões, com comparação pareada, e aparece nos três modelos e em dois ambientes de hardware distintos. Comparação pareada tem muito mais poder que comparação entre grupos — é também por isso que as instituições reportam deltas com teste pareado, não médias soltas.

Como as grandes avaliações fazem

Práticas de referência e o que este projeto adota de cada uma.

Instituição / frameworkPráticaAqui
EleutherAI
lm-evaluation-harness		 Não pede a letra: pontua cada alternativa por log-likelihood e escolhe a de maior probabilidade. Reporta acc e acc_norm (normalizado por bytes, para não penalizar alternativas longas). Não adotado — o Ollama não expõe log-probs por alternativa. Compensamos com saída estruturada (enum), que elimina erro de parsing.
Stanford CRFM
HELM		 Roda a mesma questão em modos de adaptação diferentes (joint × separate) porque a escolha muda o resultado drasticamente — OPT-175B vai de 79,1% a 30,2% no HellaSwag só trocando o modo. Adotado em espírito: reportamos duas condições lado a lado em vez de um número só.
TIGER-AI-Lab
MMLU-Pro		 Ampliou de 4 para 10 alternativas justamente para reduzir sensibilidade a prompt e posição: a variação entre 24 estilos de prompt caiu de 4–5% para 2%. Mantidas 5 alternativas (requisito do trabalho); o viés residual é medido, não ignorado.
Zheng et al. (ICLR 2024) Mostram flutuação de ~10–15 p.p. só movendo a posição do gabarito, e recomendam permutação cíclica — a permutação completa custaria k! passadas. Adotado diretamente: é o modo cíclico com 5 rotações.
LMArena
ex-LMSYS Chatbot Arena		 Controla viés posicional apresentando cada par nas duas ordens e só contando vitória se ela se mantém nas duas. Ranking por Bradley-Terry com IC por bootstrap. Mesma lógica: o resultado que sobrevive à troca de posição é o que conta.
Anthropic
Miller (2024)		 Reportar erro-padrão sempre; agrupar por questão quando há repetições; usar teste pareado para comparar modelos; fazer análise de poder antes de rodar. Adotado: IC 95% agrupado por questão em summary.json, exibido como bigode no gráfico.

Reproduzir localmente

git clone https://github.com/gutoportelaa/piaui-bench
cd piaui-bench

ollama pull llama3.2:3b
ollama pull qwen3:4b
ollama pull gemma3:4b

python3 bench/run_bench.py --modo fixa    --runs 1
python3 bench/run_bench.py --modo ciclica --runs 5 --out docs/results_shuffle.json
python3 bench/consolidar.py               # tabela do relatório + summary.csv

python3 -m http.server -d docs 8000       # abre http://localhost:8000
